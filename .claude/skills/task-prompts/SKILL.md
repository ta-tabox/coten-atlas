# 次に着手する issue を選び、貼るためのプロンプトを出す

人間は、このスキルが出したプロンプトを、issue ごとか組ごとに新しいセッションへ貼る。
このスキルは、どの issue を今着手できるか、どの issue を一つのセッションで順に進めるか、各セッションをどのモデルで立てるかを決めて、プロンプトの形で出す。
プロンプトの文面の型は同じディレクトリの `templates.md` が持つ。

着手の順序の正は `docs/ROADMAP.md`「公開画面の順序」と「依存グラフ」で、このスキルは順序を写さない。
このスキルが持つのは、順序と issue の状態を突き合わせる手順と、組の切り方と、モデルの選び方である。

## 流れ

| 順 | 手順 | 出すもの |
|---|---|---|
| 1 | 状態を取得する | 開いている issue と PR の一覧、main の `docs/ROADMAP.md` |
| 2 | ROADMAP を状態に合わせる | 閉じた issue を表から消すコミット（残っていたときだけ） |
| 3 | 着手できる issue を選ぶ | 候補の issue と、外した issue の理由 |
| 4 | 組に分ける | 組ごとの形（単独・オーケストレーター） |
| 5 | モデルを決める | セッションごとの推奨モデル |
| 6 | プロンプトを出す | 組の表と、組ごとのプロンプト |

## 1. 状態を取得する

- `git fetch origin main` の後、`docs/ROADMAP.md` は `git show origin/main:docs/ROADMAP.md` で読む
  手元のブランチは古いことがある
- issue と PR は REST で取得する
  このセッションの `gh` は GraphQL を 403 で拒否するので、`gh issue list` と `gh pr list` は使えない
  - issue は `gh api 'repos/ta-tabox/coten-atlas/issues?state=open&per_page=100' --paginate` で取得し、`pull_request` を持つ行は PR として分ける
  - 一つの issue の状態は `gh api repos/ta-tabox/coten-atlas/issues/<N> -q .state` で確かめる
- 候補になる issue は、本文と全コメントを読む
  本文の「前提」「並行の注意」「触らないもの」と、人間の決定のコメントが、手順 3 と 4 の材料になる
  本文より後に書かれたコメントが、本文の事実を覆していることがある

## 2. ROADMAP を状態に合わせる

`docs/ROADMAP.md` は閉じた issue を表から消す規則を持つ（同文書「この文書は状態を持たない」）。
閉じた issue が「公開画面の順序」の表か「同じファイルを取り合う」の表に残っていたら、プロンプトを出す前に消す。

- 消した結果、先に閉じる issue がすべて消えた行は、先に閉じる issue を「なし」にして順の番号を詰める
- 手順 4 で順序を新しく決めたら、同じコミットで表の「先に閉じる issue」と「なぜこの順か」にも書く
  順序の理由はコミットの本文に書く
- `docs/ARCHITECTURE.md` §8 に閉じた issue の番号が残っていれば、同じ PR で消す（`.claude/rules/writing.project.md`）
- コミットは `web/` で `pnpm check` が緑になってから作る
  PR の作成は、`CLAUDE.md` の git 節のとおり、人間が指示したときだけにする

## 3. 着手できる issue を選ぶ

次の三つをすべて満たす issue を候補にする。

- `docs/ROADMAP.md` の表で、先に閉じる issue がすべて `closed` である
- 本文の「前提」に挙がった issue がすべて `closed` である
  「前提」の番号が古く、コメントが読み替えを指示していれば、読み替えた番号で判定する
- 人間の決定を待っていない
  本文の「決めること（人間）」が未決のまま残る issue と、人間の作業（アカウントの登録・キーの発行・外部への問い合わせ）が済んでいない issue は外す

ROADMAP の表に載らない issue も、上の三つを満たし、表の issue と設計がぶつからなければ候補にしてよい。
外した issue は、番号と題と外した理由を一行ずつ出力に書く。

## 4. 組に分ける

二つの issue を並行させるか、一つのセッションで順に進めるかは、触るファイルが重なるかでなく、片方の結果を前提にもう片方を作るかで決める。
同じファイルの別の行を触るだけなら、後から main へ入る PR が取り込めば済むからである。

| 判定 | 形 |
|---|---|
| ROADMAP の表で、片方がもう片方を「先に閉じる issue」に持つ | 順に進める |
| 本文の「前提」か「並行の注意」が、もう片方を名指している | 順に進める |
| 同じ部品の同じ処理（例: 地図の点のポインタの処理）を、両方が変える | 順に進める |
| 片方が main へ先に入ると、もう片方が入るまで画面が崩れる | 順に進め、マージの順を PR の本文に書く |
| 同じファイルの別の行だけが重なる | 並行させ、プロンプトに重なる行を書く |
| 重なるファイルが無い | 並行させる |

- 順に進める組は、オーケストレーターのプロンプトにする（`templates.md`「オーケストレーター」）
- 一つだけの issue は、単独のセッションのプロンプトにする（`templates.md`「単独のセッション」）
- 組の中の issue は 1 issue = 1 PR を保ち、後ろの PR は前の PR のブランチを base にする
- 組の中の最後の issue が、組の外の issue がすべて閉じるのを待つときは、その条件をオーケストレーターのプロンプトの「着手の条件」に書く

## 5. モデルを決める

セッションごとに推奨モデルを決め、出力の組の表と各プロンプトの直前に書く。

| セッション | 推奨モデル | 理由 |
|---|---|---|
| オーケストレーター | `claude-sonnet-5-5` | `gh api` と `git merge` の決まった操作だけをする |
| サブと単独のセッション（既定） | `claude-sonnet-5-5` | issue の本文が作るものと完了条件を値まで決めている |
| サブと単独のセッション（未決が残る issue） | `claude-opus-5-5` | 本文に「実装で決めること」が残り、決め方の基準が本文と決定のコメントに無い |
| サブと単独のセッション（人間の原文をまとめる issue） | `claude-opus-5-5` | 原文に無い経験を足さない判断が要る |
| どのセッションでも | `claude-haiku-5-5` は使わない | PR の本文とコミットの本文が `.claude/rules/writing.md` の規律を満たさないと、人間の差し戻しで費用が逆転する |

- オーケストレーターのモデルは、人間がセッションを立てるときに選ぶので、プロンプトの外に書く
- サブのモデルは、オーケストレーターが `create_session` の `model` に渡すので、オーケストレーターのプロンプトの表に書く
- 未決が残るかは、手順 1 で読んだ本文とコメントで判定する
  判定が割れる issue は、オーケストレーターのプロンプトに「同じサブへ 2 回差し戻しても緑にならなければ、同じブランチの先端から `claude-opus-5-5` のサブを立て直す」を残す

## 6. プロンプトを出す

出力は次の順にする。

1. 組の表
   列は「セッション・形・issue（順に並べる）・推奨モデル・着手できる時点」にする
2. 組み方の理由
   順に進める組ごとに、手順 4 のどの判定に当たったかを一行で書く
3. 外した issue と理由
4. プロンプト
   各プロンプトの直前の行に、そのセッションの推奨モデルを書く
   プロンプトは `templates.md` の型の変数を埋めたもので、1 つのプロンプトを 1 つのフェンスに収める
5. マージの順
   組の外の PR どうしで順を持つものだけを書く

プロンプトを書くときは次を守る。

- issue の本文を写さず、本文を読む指示と、本文に無いことだけを書く
  本文に無いことは、本文より後に変わった事実（先に main へ入った PR が変えたファイル）と、並行するセッションと重なる行である
- 並行するセッションの issue を番号と名前で挙げ、重なるファイルと行を書く
- 本文の事実が古いと分かっていれば、どの PR で何が変わったかを書く
- フェンスの長さは、中身の最も長いバッククォートの連より 1 本多くする
  オーケストレーターのプロンプトはサブのプロンプトをフェンスごと持つので、外側を 5 本にする

## 人間が送る指示

オーケストレーターは、人間が送る次の指示でだけ動く。
サブはオーケストレーターへ報告せず、PR を作ったら止まるので、オーケストレーターの消費はこの指示の数に比例する。

| 送る時点 | 送る文 |
|---|---|
| サブが PR を作ったのを GitHub で見た | `次へ` |
| 組の中の前の PR をマージした | `マージした #<PR 番号>` |
| 前の PR にレビューの修正を push させた | `直した #<PR 番号>` |
| どこまで進んだかを知りたい | `状況` |

レビューの修正そのものは、人間が PR を作ったサブのセッションへ直接頼む。
積み直しは rebase でなく `git merge` と通常の push で行う。
main が merge commit で PR を取り込むので、前の PR がマージされても、後ろの PR は base を main へ替えるだけで差分が正しくなるからである。
