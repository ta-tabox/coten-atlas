# 歴史の見直し — 仮決定を採用し、見直す論点を issue にする

シリーズの値を足す・直す PR は、代表点の選択や年の端の多くを Claude の仮決定で置き、候補と覆りうる根拠を `docs/sources/<シリーズ id>.md` の「仮決定と論点」節に残す。
論点の数が多いと、人間が PR の中で全部を見ることはできない。
そこで、人間が仮決定をまとめて採用して一度決着させ、ゆっくり見直す価値のある論点だけを、1 件ずつ開いて決められる issue にする。

- ラベル `history-review`（補助: 採用済みの歴史データを人間が一件ずつ見直す）と `human` を付ける
- 一覧は `gh issue list --state open --label history-review` か、GitHub の `label:history-review` で引く
- 手本は #174（紫式部の代表点。代表点の選択と未確認の座標の二論点）・#178（鎌倉武士の `timeRange` の終わり）・#180（ムガール帝国の代表点と `region`）と、PR #167（中世の 11 シリーズを series.json へ載せる）の本文の「人間に見てほしい」節である

このスキルは二つの手順を持つ。

| 手順 | いつ行うか | 出すもの |
|---|---|---|
| A. 切り出す | 人間が PR の仮決定の採用を決めたとき | 見直しの issue・書き換えた典拠のファイル・PR 本文 |
| B. 決定を反映する | 見直しの issue に人間が決定をコメントしたとき | 決定を記録して issue を閉じる PR |

## A. 切り出す

### 1. 論点を選ぶ

PR 本文の「人間に見てほしい」節と、対象の全シリーズの典拠のファイルの「仮決定と論点」節を読み、次の表で振り分ける。

| 振り分け | 当たる論点 |
|---|---|
| issue にする | 事績の中心の候補が各回の配分から一つに絞り切れず、別の候補を採ると代表点が別の都市へ動く |
| issue にする | `timeRange` の端の選び方で、era スライダーに濃く出る期間が大きく変わる |
| issue にする | 座標や地点の事実を典拠で確かめられていない |
| issue にする | `region` の選び方が割れる |
| 仮決定で決着とする | 生没年の並立説・綴りの揺れ・同じ都市の中での数百 m の座標の差・規則で一つに決まった論点 |

1 シリーズに issue にする論点が複数あれば、1 件にまとめる。
決着とする論点は、典拠のファイルに残すだけで issue にしない。

### 2. issue を起こす

題は `見直し: <シリーズ名>（<シリーズ id>）の<論点>を<A>と<B>のどちらにするか` の形にする。
ラベルは `history-review` と `human` を付ける。

```bash
gh issue create --label history-review --label human \
  --title '見直し: 鑑真（ganjin）の代表点を奈良と揚州のどちらにするか' --body-file <本文のファイル>
```

本文は次の節にする。

```markdown
**前提**: PR #<番号>（<PR の題>）のマージ ／ **担当**: 判断は人間、反映は Claude ／ **参照**: `docs/sources/<シリーズ id>.md`、skill `series-vocabulary` の手順 <N>

## 目的

`<シリーズ id>`（<シリーズ名>）の<論点>について、PR #<番号> の仮決定を採用したうえで、ゆっくり見直す。
仮決定の値のまま main に入るので、この issue を見直す前でも地図とデータは壊れない。

## いまの値（採用済み）

| 欄 | 値 |
|---|---|

## 見直す論点

### 1. <論点>

<規則がどこまで決め、どこから番組の内容の判断かを 1〜2 文で>
<各回の配分（第 N〜M 回が〜を扱う）>

| 案 | <欄> | 根拠 | 起きること |
|---|---|---|---|
| A（採用中） | | | |
| B | | | |

## 決め方

- 決定をこの issue にコメントする（「A のまま」でもよい）
- Claude が決定を `docs/sources/<シリーズ id>.md`（値を変えるなら `catalog/` も）へ反映する PR を開き、`closes` でこの issue を閉じる。
  値を変えない決定は、複数の見直しの issue をまとめて 1 本の PR で反映してよい

## 完了条件（機械判定）

- `web/` で `pnpm check` が緑
- `docs/sources/<シリーズ id>.md` の「仮決定と論点」が、この issue の決定を記録している

## 人間の判定

<論点ごとに選ぶもの>
```

「起きること」には、案を採ったときに地図の上で何が変わるか（点が動く距離・点と `region` の区画が食い違って見えるか・era スライダーに濃く出る期間）と、座標の典拠が取れているかを書く。

### 3. 典拠のファイルを書き換える

対象の全シリーズの「仮決定と論点」節を、次のように書き換える。

| 書き換える所 | issue を切り出したシリーズ | それ以外のシリーズ |
|---|---|---|
| 地の文の「人間の判定は [#<PR 番号>](<PR の URL>) で待っている。」の行 | `<日付> に人間が仮決定を採用して決着させ、見直しを [#N](<URL>)（<論点>）へ切り出した。` | `<日付> に人間が仮決定を採用して決着させた。` |
| 表の「覆りうる根拠」の列で、人間の判定を待つと書いた文（例: 「事績の中心をどこに置くかは人間の判定を待つ」） | `見直しは #N で行う` | 文ごと消す |
| 「裏どりの出所」表 | `\| [#N（見直し）](<URL>) \| 採用した仮決定を人間が見直す論点と案 \|` の行を足す | 変えない |

地の文の行は「人間の判定は」と「で待っている」の間に PR のリンクを挟むので、固定の文字列でなく正規表現で探す。
書き換えた後に、次のコマンドが何も返さないことを確かめる。

```bash
grep -nE '人間の判定(は|を).*待' docs/sources/<シリーズ id>.md
```

### 4. PR 本文を書き換える

「人間に見てほしい」節を、次の内容に差し替える。

- **merge を妨げない** の一行
- 人間が仮決定をすべて採用して決着させたこと
- 見直しの issue の表（issue・シリーズ id・見直す論点）
- 切り出した基準（手順 1 の表の「issue にする」の 4 項目）と、それ以外を決着としたこと
- 見直しの流れ（PR が main に入った後に 1 件ずつ見る・人間が決定をコメントし Claude が反映の PR で閉じる・`label:history-review` で引ける）

本文の他の節に「人間の判定を待つ」と書いた文があれば、「人間が仮決定を採用した」に直す。

### 5. 検査してコミットする

`web/` で `pnpm check` を緑にし、`docs(sources): <PR の対象>の仮決定を採用して決着とし、見直しの論点を issue へ向ける` の 1 コミットにして push する。
`catalog/` の値は変えない。

並行するセッションの PR は、そのセッションが自分の PR で A を行う。
他のセッションの PR のブランチへは push しない。

## B. 決定を反映する

見直しの issue に人間が決定をコメントしたら、決定ごとに次を行う。

| 決定 | 行うこと | コミット |
|---|---|---|
| 仮決定の値のまま | 典拠のファイルの「仮決定と論点」の「見直しは #N で行う」を「#N で人間が仮決定のまま決着させた」に直す | `docs(sources):` |
| 値を変える | skill `series-vocabulary` の手順で新しい値（代表点・事物の `id`・`region`・`timeRange`）を決め、`catalog/` と典拠のファイルを直す。新しい地点の事実と座標は、skill `series-survey` の手順 6 で `@historian` に確かめさせる | `fix(catalog):` と `docs(sources):` |

1. `main` からブランチを切る。
   値を変えない決定を複数まとめるなら `docs/history-review-<日付>`、値を変えるなら `fix/history-review-<シリーズ id>` にする
2. 代表点や事物の `id` を動かしたら、skill `series-survey` の手順 2 の集計で、他のシリーズと同じ事物の `id` や同じ地名を要求していないかを確かめる
3. 典拠のファイルの「代表点」節や鍵の表も、新しい値へ直す。
   変える前の値は、候補の表に「見直し前の値」として残す
4. `web/` で `pnpm check` を緑にして push し、PR を開く。
   本文に、反映した issue ごとに `closes #N` を書く
5. マージは人間が指示したときだけ行う
