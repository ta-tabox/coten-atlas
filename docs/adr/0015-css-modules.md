# 0015. スタイルは CSS Modules で書き、CSS フレームワークを入れない

- **状態**: 採用
- **決定日**: 2026-08-28
- **関係する ADR**: 0001、0004

## 文脈

いま `web/` が持つ CSS は `src/app/globals.css` の 1 枚で、中身は `body { margin: 0 }` の 1 規則だけである。
CSS フレームワークは入っていない。

#2（S1・ベースマップの全画面表示）のレビューで「インラインスタイルはできるだけ避けたい。tailwind などに寄せるか、class として定義する形にしていきたい」という指摘が出た。
その場は `<body style={{ margin: 0 }}>` を `globals.css` へ移して収めたが、書き方そのものは決めていない。

これから S4（era スライダー）・S5（パネルと詳細カード・関連テーマ行・tag 絞り込み）・S8（フッタと `/about`）でスタイルが増える。
コンポーネントで 8 前後、CSS で 400〜500 行のオーダーになる見積もりで、全画面マップの上に載る overlay が中心になる。
増え始めてから決めると、決める前に書いた分と後の分で書き方が混ざる。

制約が二つある。
attribution の位置と背景を持つのは `maplibre-gl.css` で、その表示は OpenFreeMap の利用条件（0004）なので、崩れは規約違反に直結する。
`output: "export"`（0001）なので、実行時に CSS を生成する仕組みは採れない。

## 決定

**CSS Modules で書く。CSS フレームワークは入れない。**

- コンポーネントごとに `Component.module.css` を併置し、`Component.tsx` から import する
- `globals.css` が持つのは、全体に効く最小の規則と、色・余白・z-index の CSS 変数だけにする。個別のコンポーネントのクラスは置かない
- 適用はいまから始める。次にスタイルが増える S4 が、最初の `*.module.css` と `globals.css` のトークンを置く

react-map-gl の `style` prop（`MapCanvas.tsx` の `width` / `height`）はコンテナの寸法を渡すコンポーネント API なので、この決定が禁じるインラインスタイルには当たらない。

## 理由

規模がフレームワークの採算点に届いていない。
ユーティリティクラスが報われるのは同じ組み合わせが何度も現れる規模で、8 コンポーネント・500 行はそこに達しない。
`CODING.md` の YAGNI（推測で汎用化しない・抽象は 2〜3 例目が現れてから抽出する）に従えば、いまは依存ゼロの側を採ることになる。

クラス名の衝突を、規約でなく構造で防げる。
CSS Modules はビルド時にクラス名をハッシュ化するので、複数のコンポーネントが同じ `.panel` を名乗っても混ざらない。

attribution が崩れる経路をそもそも作らない。
CSS Modules は reset を持ち込まないので、`maplibre-gl.css` に触れる規則が生まれない。

static export との噛み合わせを検証する必要が無い。
CSS Modules は Next.js の標準機能で、ビルド時に閉じることを Next 自身が保証する。

### 素の CSS 1 枚を続けなかった理由

追加はゼロだが、8 コンポーネント分のクラス名が単一の名前空間へ積み上がる。
命名規約を決めなければ S5 で衝突し、決めればそれを人間が守る費用が毎回かかる。
コンポーネントが 2〜3 個で終わる見積もりなら、これを採っていた。

### Tailwind を採らなかった理由

`output: "export"` とは衝突しない。
v4 の生成は `@tailwindcss/postcss` が `next build` の中で行うので、実行時の CSS 生成にはならない。

`maplibre-gl.css` を壊す確度も低い。
v4 は生成物を丸ごと `@layer theme, base, components, utilities` へ入れ、カスケードレイヤはレイヤなしの規則がレイヤ付きの全規則に勝つので、レイヤなしで import される `maplibre-gl.css` は preflight に潰されない。
ただしこれは机上の判断で、実測はしていない（この決定は実装を触らない）。
裏返しとして、maplibre が持つ要素へユーティリティを当てても、レイヤ付きの側が負けて効かない。

採らなかったのは規模の理由による。
ビルド依存にネイティブバイナリ（`@tailwindcss/oxide`）が 1 つ増える分と、`className` が横に伸びる分を、いまの規模では回収できない。

## 帰結

- 導入のための issue は起こさない。設定も依存追加も無いので、S4 が最初の 1 枚を書いた時点で適用が始まる
- **S4 の issue は `globals.css` のトークン定義を含む**。色・余白・z-index を各モジュールが個別に決めると、後から揃え直す作業が S8 に乗る
- overlay の重なり順は `globals.css` の z-index 変数が一箇所で持つ。全画面マップの上にスライダー・パネル・詳細カード・フッタが載るので、モジュールごとに数値を書くと突き合わせられなくなる
- Biome は `web/biome.json` の `includes` が `**` なので、`*.module.css` を足せばそのまま整形と検査に載る。設定の追加は要らない（実測で確認した）
- **CSS のコメントは機械が見ない**。`scripts/lint-comments.ts` の対象は `.ts` / `.tsx` / `.mts` だけなので、`CODING.md` のコメント規約は人間が守ることになる
- JSX のインラインスタイルは使わない。コンポーネント API が寸法や座標を要求する場合だけが例外
- CSS-in-JS へは寄せない。実行時にスタイルを生成する層は `output: "export"` と噛み合わない
- **この決定が扱うのは DOM のスタイルだけ**。`kind` による地物の描き分け（`ARCHITECTURE.md`「データモデル」）は MapLibre の layer paint プロパティなので、`*.module.css` には書けない

## 覆る条件

S5 を書き終えた時点でユーティリティの重複が実際に痛いとき、あるいはコンポーネントが見積もり（8 前後）の倍を超えたとき。
そのときは新しい ADR で supersede し、移行の範囲（新規だけをフレームワークで書くか、既存も書き換えるか）を併せて決める。

複数人で書くようになったときも同じ。
命名の揺れを規約でなくフレームワークの語彙で抑える方が安くなる。
