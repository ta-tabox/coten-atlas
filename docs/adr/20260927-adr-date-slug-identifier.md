# ADR の識別子を決定日と slug にする

- **状態**: 採用
- **決定日**: 2026-09-27
- **関係する ADR**: なし

## 文脈

連番の識別子は、次の値を既存の一覧から決める。
一覧は未マージのブランチが足す ADR を知らないので、並行するセッションが同じ番号を取っても、後からマージする PR まで衝突に気付けない。
番号を取った PR が取り下げられると欠番が残り、欠番を作らないために後ろを繰り下げると、その番号を名指す参照まで動く。

## 決定

ADR の識別子を `YYYYMMDD-<slug>` にする。
`YYYYMMDD` はヘッダの決定日、`<slug>` は決定を表す英小文字・数字・ハイフンの語句である。

既存の 46 本は全件を新しい識別子へ改名し、`docs/adr/README.md` の一覧に `旧番号` の列を残す。
旧番号を名指す open な issue と PR の本文は書き換えず、`旧番号` の列から新しい識別子を探させる。

ADR の外から指すときの書式は `ADR-<識別子>（決定の名前）` にする。

規約の全文は `docs/adr/README.md` が持つ。

## 理由

- 決定日と決定の内容は、書き手が他のブランチの状態を見ずに単独で知っている値である
- 同じ日に同じ slug が並ぶ事故は、git が同じパスの追加として衝突させるので、マージの前に分かる
- 識別子が slug を持つので、ファイル名だけでどの決定かが読める
- **連番のまま続ける** ／ 並行するブランチが同じ番号を取る事故が残り、一覧を見るだけでは防げない
- **supersede されていない 36 本だけ改名する** ／ 2 つの形が並び、supersede の連鎖が番号と識別子をまたぐ
- **既存を据え置き、新しい ADR からだけ新しい形にする** ／ 一覧が 2 つの形で並び続け、どちらの形で書くかを毎回判断することになる
- **open な issue と PR の本文も書き換える** ／ 本文の更新が通知を飛ばし、レビューの文脈が進行中の PR でずれる

## 帰結

- `docs/adr/` の 46 本のパスが変わり、リポジトリの中でそれらを名指す 81 本のファイルの参照が識別子へ変わる
- 一覧は識別子の辞書順に並ぶので、決定日順と一致し、旧番号の順とは一致しない
- 旧番号の順に依存していた注記（「0019 までのレコードは」）は、番号でなく決定の内容で範囲を書く
- 新しい ADR を足す位置は一覧の末尾でなく、決定日が決まる位置になる

## 覆る条件

- 同じ決定日と同じ slug の衝突が繰り返し起き、slug を変える判断が書き手の負担になったとき
- レコードが増えて、辞書順の一覧から目的の決定を見つけられなくなったとき
